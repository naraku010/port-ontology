# 알려진 한계와 다음 작업 후보

## 알려진 한계

- **영속성 없음**: 상태는 메모리에만 있습니다. 앱을 끄거나 초기화하면 시드 상태로 돌아갑니다.
- **앱과 MCP 서버가 상태를 공유하지 않음**: 별도 프로세스입니다. LLM이 적용한 계획이 열려 있는 앱 화면에 나타나지 않습니다.
- **지연 시나리오는 하나씩**: 여러 항차가 동시에 늦는 경우를 한 번에 시뮬레이션하지 않습니다.
- **연쇄는 선석 안에서만**: 크레인 배분, 야드 혼잡, 게이트·내륙 운송으로의 전파는 모델에 없습니다.
- **R4, R5는 검사만**: 야드 재배치 제안(propose) 도구는 아직 없습니다.
- **위험물 격리표는 단순화**: 실제 IMDG 격리표가 아닙니다.
- **시간 기준**: 타임존이 없는 로컬 시각이며 계획 기간(4일)이 고정입니다.
- **실데이터 없음**: 공개 입출항 데이터(Port-MIS 등)나 AIS를 아직 연결하지 않았습니다.

## 다음 작업 후보 (우선순위 순)

1. **상태 저장과 공유**: 앱 데이터 폴더에 JSON(또는 SQLite)으로 저장하고, MCP 서버가 같은 파일을 읽고 쓰게 합니다. 앱은 파일 변경을 감지해 새로 고칩니다. 그래야 "LLM이 제안 → 사용자가 앱에서 적용" 데모가 됩니다.
2. **벡터 RAG와 비교 평가**: 같은 질문 세트로 일반 문서 RAG와 이 온톨로지 방식의 정답률을 비교하는 스크립트와 결과표. 포트폴리오 설득력이 가장 크게 올라가는 항목입니다.
3. **복수 지연 / 기상 이벤트**: `WeatherEvent` 클래스를 추가하고 영향 해역의 여러 항차를 한 번에 지연시킵니다.
4. **야드 재배치 액션**: `propose_yard_move`(R4, R5 검증)와 리퍼 플러그 부족 시 대안 블록 제시.
5. **실데이터 연결**: 공공데이터포털 입출항 정보로 항차를 만들고, 컨테이너는 합성으로 얹습니다.
6. **앱 안 LLM 대화창**: 사용자 PC의 CLI를 비대화형으로 호출해 앱 안에서 질문하고, 응답에 포함된 근거 경로를 그래프에 강조합니다. CLI가 없으면 비활성화합니다.
7. **OWL/SHACL 내보내기**: 스키마와 규칙을 표준 형식으로 내보내 다른 도구와 호환됨을 보여줍니다.
